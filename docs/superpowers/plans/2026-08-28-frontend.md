# Frontend `photo_ui` — plan d'implémentation

> **Pour les agents d'exécution :** SOUS-COMPÉTENCE REQUISE — utiliser
> `superpowers:subagent-driven-development` (recommandé) ou
> `superpowers:executing-plans` pour exécuter ce plan tâche par tâche. Les étapes
> utilisent la syntaxe case à cocher (`- [ ]`).

**But :** livrer l'atelier web qui permet à un utilisateur de composer, à partir
de 3 930 photos et de 1 859 passages de texte, le dossier qu'un LLM utilisera
pour écrire une bande dessinée — sans jamais présenter une date inférée comme une
date lue.

**Architecture :** SPA React + Vite, TypeScript strict. Trois couches étanches :
`domain/` (règles pures, sans React ni réseau), `api/` (contrat REST validé par
Zod à l'exécution), `ui/` + `screens/` (rendu). L'état serveur est détenu par
TanStack Query ; l'état des filtres vit dans l'URL, jamais dans un store — un
filtre qui n'est pas dans l'URL est un filtre qui peut disparaître en silence
(§6.5). Aucun store global. Le développement et les tests se font contre MSW,
qui implémente le contrat REST gelé, ce qui rend le frontend indépendant du
calendrier du backend.

**Pile technique :** Vite 8.2 · React 19.2 · TypeScript 7.0 (`strict`) ·
React Router 8.3 · TanStack Query 5.102 · Zod 4.4 · MSW 2.15 · Vitest 4.1 +
`@testing-library/react` 16.3 + jsdom 30 · Playwright 1.62 · ESLint 10.9 +
typescript-eslint 8.68 · CSS Modules + propriétés personnalisées.

**Spécification :** `docs/frontend-spec.md`. Le plan argumente à partir d'elle ;
les deux voyagent ensemble. Références amont : `docs/pipeline-inventory.md`,
`docs/pipeline-capabilities.md`.

## Contraintes globales

Ces exigences s'appliquent implicitement à **toutes** les tâches.

- **Une inférence ne doit jamais ressembler à une lecture** (§7.1). Trois natures
  jamais fusionnées : `reading` (vert, romain), `inference` (ambre, italique,
  `≈`), `decision` (violet, gras, `✓`). La règle tient structurellement : un seul
  composant a le droit de rendre une date, et un test de source le vérifie.
- **Ne jamais écarter ce qui pourrait correspondre** (§7.3). Un intervalle qui
  **chevauche** est retenu, jamais « doit être contenu ». Le doute inclut.
  Ce qui est écarté se compte et s'affiche.
- **On ratisse large, on ne raconte pas large** (§7.3). Élargir un filtre
  n'élargit jamais ce qu'on affirme.
- **Absent n'est pas zéro** (§7.4). NULL remonte NULL. L'interface affiche
  `sans date`, `sans position`, jamais une valeur par défaut lisible comme une
  donnée.
- **Clés durables** : `cloud_asset_id` pour une photo, `sha256` pour son contenu
  et sa vignette, identifiant textuel (`ma-vie/p007/002`) pour un texte. **Jamais
  `photos.id`** (§7.4).
- **Jamais de chaîne de date pré-formatée dans le contrat** (§9.6.4). Bornes,
  nature, source, précision sont cinq champs séparés.
- **Aucun chemin en dur.** Tout par variable d'environnement, préfixe `VITE_`.
- **Aucune écriture** hors de `/Users/nico/projects/photo_ui`. Le volume
  `/Volumes/OWC Envoy Ultra` et `/Users/nico/projects/adobe_mcp` sont en lecture
  seule, caches compris (§7.2).
- **Responsive et tactile** : cibles de 44 px minimum, aucune action accessible
  seulement au survol ou au clic droit (§1.2).
- **Langue** : interface et documents du projet en français ; code, noms de
  symboles, commentaires et messages de commit en anglais.
- **TypeScript strict**, aucun `any`. Types de retour explicites sur les API
  publiques. Commits conventionnels (`feat:`, `fix:`, `test:`, `chore:`).
- **Tests colocalisés** : `foo.ts` → `foo.test.ts`.

## 1. Faut-il un backend pour implémenter le frontend ?

**Non pour le construire et le tester, oui pour s'en servir.** La dépendance
réelle n'est pas l'implémentation du backend, c'est **le gel du contrat REST**.

### 1.1 Ce qui est strictement impossible sans processus serveur

| Besoin | Pourquoi aucun navigateur ne peut le faire |
|:---|:---|
| Lire les 4 SQLite du pipeline et PostgreSQL | Pas de système de fichiers, pas de socket TCP vers Postgres. |
| La cascade de datation (§3) | La spec impose qu'elle soit **calculée une fois à l'import et stockée** (§3.6). C'est du travail serveur par construction, et la recalculer côté client la ferait diverger. |
| Écrire le dossier livré dans `TASKS_ROOT` (§1.3, §5.6) | Aucune API navigateur n'écrit un répertoire idempotent à un chemin configuré. La File System Access API exige un sélecteur par répertoire à chaque geste et ne survit pas au ré-export. |
| Le rendu 1400 px | `sips` est un processus (§9.2). |
| Persister tâches, sélections, notes, corrections (§9.3, §9.4) | Rien ne survit à la fermeture de l'onglet. |
| Recherche plein texte `pg_trgm` + `unaccent` en français (§9.2) | Côté base. |
| Servir les pixels en production | Vignettes, images de pages, rendus : il faut un serveur de fichiers. |

### 1.2 Ce que le frontend développe et teste sans backend, et par quel moyen

- **Toute l'interface**, et surtout **la règle capitale** : la fonction
  `(resolved_kind, resolved_precision, bornes) → chaîne rendue + traitement
  visuel` est de la logique frontend pure. C'est elle qui doit être testée à
  mort, et elle ne dépend d'aucun serveur.
- **Les données** : MSW (Mock Service Worker) intercepte `fetch` dans trois
  environnements avec **un seul jeu de gestionnaires** — le navigateur en
  développement, jsdom pour les tests de composants, Node pour Playwright. Les
  gestionnaires implémentent le contrat gelé et tiennent un magasin en mémoire,
  donc les écritures (sélectionner, noter, corriger) font un aller-retour réel
  dans la session.
- **Les pixels** : les 3 925 vignettes 224 px **existent déjà sur disque**
  (`work/content-thumbs/<sha256>.jpg`, 1 Go, vérifié). Un script à sens unique
  les recopie **en lecture seule** vers `public/thumbs/` dans le projet. 48
  vignettes réelles sont versionnées avec les fixtures pour que la CI n'ait
  jamais besoin du volume ; le miroir complet (≈ 92 Mo sur le périmètre) est
  ignoré par git et se régénère à la demande.
- **L'export** : le frontend ne construit pas le manifeste — il déclenche,
  affiche la progression, rend le rapport. C'est donc le déclenchement, la
  progression, l'annulation et les trois modes d'échec qui se testent, contre un
  gestionnaire MSW qui les simule. Honnête : on teste ce qu'on écrit.

### 1.3 Ordre de travail recommandé et points de synchronisation

Les deux chantiers avancent **en parallèle**, pas en séquence. Ce qui les relie :

- **SP1 — gel du contrat, avant toute ligne de code applicatif.** Un artefact :
  les schémas Zod de `src/api/contract/`, dérivés de §9. C'est la seule
  dépendance dure, et elle coûte une journée. Le backend l'implémente, le
  frontend le simule. *(Voir la question bloquante en §9 de ce plan.)*
- **SP2 — l'import backend tourne, `GET /photos` répond sur les données
  réelles.** Le frontend bascule son environnement de développement de MSW vers
  le serveur par une variable d'environnement, et enregistre un vidage réel en
  fixture. **Tout ce qui n'est pas mesurable avant l'est à partir d'ici** : le
  rendement réel du recouvrement après cascade (incertitude n° 4 de la spec), le
  compte des écartés, la tenue de la grille sur 3 930 tuiles.
- **SP3 — l'export écrit vraiment.** Ferme la tranche 1.

**La dérive de contrat est détectée mécaniquement** : les mêmes schémas Zod
valident les fixtures MSW *et* les réponses réelles. Un champ renommé côté
backend fait échouer `npm run contract:check` en nommant le champ, au lieu de
produire un `undefined` qui s'affiche comme une donnée manquante.

## 2. Découpage en tranches

Ordre de livraison. Chaque tranche est utilisable seule.

| # | Tranche | Ce qu'elle donne à Nicolas |
|---:|:---|:---|
| **1** | **La colonne vertébrale : une tâche, une grille, un dossier** | Le plus petit produit qui serve : créer une tâche, filtrer par album et par plage de dates, sélectionner, revoir, **exporter un dossier sur disque**. Sans export, rien n'est livré. |
| **2** | **Le texte** | Écran texte à trois sections, page en regard, sélection de passages, recouvrement dans les deux sens, ordre du manifeste réordonnable. **Plus les notes libres** — Q1(a) fait des notes le seul texte possible pour les 2 041 photos de 2003-2004. |
| **3** | **Chercher** | Tags IA par sélectivité décroissante, personnes, OCR, lieu avec repli sur `albumPath`/`groupName`, recherche plein texte, jetons de filtres, compte des écartés et geste de rappel. |
| **4** | **Écrire** | Correction de transcription, saisie de `ref.album_span` sur les 25 albums pré-listés, `ref.web_span`. |
| **5** | **La revue en entier** | Chronologie images/textes sur un axe, bandeau de contrôle à cinq compteurs, gestion complète des tâches, états d'export, volume démonté en session. |

**Pourquoi cet ordre.** La tranche 1 produit le livrable ; sans elle rien n'est
délivrable. La tranche 2 apporte la matière textuelle, qui est la moitié du
dossier. Les notes migrent de la tranche 4 vers la tranche 2 parce que le journal
s'arrête le 2 juin 2002 et que 2 041 photos n'auront jamais d'autre texte que
celles-là. La recherche (3) précède l'écriture (4) parce que les tags IA sont le
seul axe de contenu et couvrent 100 % du périmètre. `ref.album_span` (tranche 4)
a le meilleur rapport effort/gain du projet — 25 saisies corrigent 421 photos —
mais son effet passe par un ré-import backend, donc son gain n'arrive pas plus
vite en la livrant plus tôt.

### 2.1 Ce que j'écarte de la V1

| Écarté | Raison |
|:---|:---|
| **Pincer pour la densité** de la grille (§5.2) | Trois points de rupture CSS suffisent. Le pincement demande une bibliothèque de gestes pour un réglage qu'on fait une fois. |
| **Balayage horizontal** sur la liste des tâches (§5.1) | Un bouton visible satisfait « aucune action derrière le survol », marche au doigt comme à la souris, et la liste compte quelques tâches. |
| **Sélection par glissé tactile** (§5.2) | « Sélectionner les N résultats » couvre le vrai besoin — un album entier d'un geste. Maj-clic reste sur pointeur. |
| **Glisser-déposer** pour l'ordre du manifeste (§5.6) | Monter / descendre / mettre en tête + saisie de position : tactile, sans dépendance. À rouvrir si l'ordonnancement d'une tâche de 200 images fait mal. |
| **Sélection d'une portion** de passage (Q2 b) | Défaut de la spec : 1 731 des 1 859 passages font moins de 400 caractères. Deux colonnes nullables suffiront le jour venu. |
| **Rendu des pages HTML du site** (Q4 b/c) | Défaut de la spec : texte seul. Thèmes FrontPage, `cp1252`, chemins relatifs — beaucoup de code pour un gain nul en V1. |
| **Virtualisation de la grille** | `content-visibility: auto` + `loading="lazy"` + boîtes à ratio fixe. **On mesure à SP2 sur 3 930 tuiles réelles**, on virtualise seulement si la mesure l'exige. |
| **Thème sombre, internationalisation** | Un utilisateur, une langue. |
| **Build Capacitor iOS / macOS** | Hors V1. Mais le responsive et les cibles 44 px se font maintenant : ils coûtent peu et se rattrapent très mal. |
| Carte, doublons, légendage VLM, export des datations, historique/annulation | Déjà hors V1 dans la spec (§8). Je ne les rouvre pas. |

## 4. Plan de tests

### 4.1 Ce qui se teste à quel niveau, et pourquoi

| Niveau | Outil | Ce qui y va | Pourquoi ici |
|:---|:---|:---|:---|
| **Unitaire** | Vitest, env `node` | `src/domain/*`, `src/api/client.ts`, `src/app/env.ts` | Fonctions pures : on peut y passer le **produit cartésien complet** des natures × précisions × bornes. C'est là que vit la règle capitale, et elle mérite l'exhaustivité, pas un échantillon. |
| **Composant** | Vitest + jsdom + RTL + MSW | `src/ui/*`, `src/screens/*` | Ce qui est visible et manipulable : la grille affiche-t-elle `octobre 1999` et non `1999-10-01` ; la tuile sans vignette nomme-t-elle son fichier ; le tiroir de filtres compte-t-il les filtres actifs. Le vrai composant contre de vraies réponses HTTP simulées — pas de mock de hook. |
| **Bout en bout** | Playwright, chromium + webkit + un viewport mobile | 6 à 8 parcours, pas plus | Seulement ce qui traverse plusieurs écrans et serait un mensonge si on le simulait : créer une tâche → filtrer → sélectionner 87 résultats → ouvrir un passage → revoir → exporter → lire le rapport. |
| **Contrat** | Vitest, env `node` | `src/api/contract/*` contre les fixtures **et** contre le serveur réel | Les mêmes schémas des deux côtés. C'est le seul mécanisme qui rend une dérive backend bruyante au lieu de silencieuse. |
| **Source** | Vitest, env `node` | `noBareDateRendering.test.ts` | Une règle d'architecture qu'aucun test de comportement ne peut attraper : elle porte sur le code qui n'existe pas encore. |

**Ce qu'on ne teste pas.** Pas de tests de capture d'écran. La règle capitale
s'assère **sémantiquement** — sur le glyphe, sur la chaîne rendue et sur un
attribut `data-date-kind` lisible par machine — jamais sur une couleur. Une
assertion de couleur est fragile, et surtout elle donnerait l'illusion de
protéger une règle que la couleur seule ne porte pas : un daltonien doit lire la
nature de la date, donc le glyphe et le libellé accessible sont le canal
principal et la couleur le second.

### 4.2 Comment on teste sans backend

Un seul jeu de gestionnaires MSW (`mocks/handlers.ts`) implémentant le contrat
gelé, monté dans trois environnements :

- **Navigateur en développement** — `mocks/browser.ts`, service worker. On
  navigue dans l'application réelle, on sélectionne, on exporte : le magasin en
  mémoire fait l'aller-retour.
- **Tests de composants** — `mocks/node.ts` dans `src/test/setup.ts`. Chaque
  test peut surcharger un gestionnaire pour produire un 400, un 500, une liste
  vide ou une réponse hors contrat.
- **Playwright** — les mêmes gestionnaires servis par le service worker.
  Déterministe, exécutable en CI, sans Postgres et sans le volume.

`VITE_API_MODE=mock | live` bascule l'ensemble. À SP2, on passe à `live` et
**les mêmes tests de contrat s'exécutent contre le vrai serveur**.

### 4.3 Les invariants qui ont leur propre test

Chacun échoue bruyamment, en nommant la règle violée.

1. **Une date inférée ne peut jamais être rendue comme une date lue.** *(La règle
   capitale.)* Test sur le produit cartésien complet : pour toute date `d` et
   tout couple de natures distinctes `k₁ ≠ k₂`,
   `render({...d, kind: k₁}) !== render({...d, kind: k₂})`. Plus les assertions
   directes : `inference` porte toujours `≈`, `decision` toujours `✓`, `reading`
   jamais `≈`.
2. **Une précision au mois n'émet jamais un jour**, et une précision à l'année
   n'émet jamais un mois — **pour les trois natures**. C'est le pendant de la
   règle 1 : §9.6.4 interdit un jour inventé au backend, celle-ci l'interdit au
   rendu.
3. **Aucun fichier hors de `src/ui/date/` ne formate une date.** Test de source
   parcourant `src/ui/` et `src/screens/`.
4. **Le chevauchement, jamais le contenu.** Cas mesuré de §7.3, verbatim : filtre
   `2000-12-01 → 2000-12-20` contre l'intervalle d'album
   `[2000-12-01, 2000-12-31]` → **retenu**. Le test documente qu'une lecture
   stricte rendrait 0 photo là où le chevauchement en rend 273.
5. **Absent n'est pas zéro.** Une photo sans date résolue affiche `sans date` ;
   sans position, `sans position`. Jamais `0`, `—`, `1970-01-01`, ni une date
   par défaut.
6. **Un filtre ne disparaît jamais.** Une réponse 400 produit une bannière
   d'erreur visible — **jamais une grille vide rendue comme « 0 résultat »**.
   C'est la distinction que le pipeline a ratée deux fois (§9.6.1).
7. **Le compte des écartés est toujours affiché** dès qu'un filtre est actif
   (§6.5, §7.3).
8. **Les trois natures de texte ne se mélangent jamais.** Une légende machine ne
   peut apparaître ni dans la liste des passages, ni dans celle des notes
   (§7.1). Garanti par le typage et vérifié par un test, parce que le manifeste
   exporté en dépend.
9. **`albumPath` est en NFD** (§9.6.6, mesuré). Filtrer sur un nom d'album saisi
   en NFC doit trouver ses photos. Le test compare `'Algès'` en NFC à la fixture
   en NFD et échoue si l'égalité littérale est utilisée quelque part.
10. **`photos.id` ne franchit jamais le contrat.** Le schéma Zod refuse un objet
    photo portant une clé `id` numérique.

### 4.4 Les jeux de données, et d'où ils viennent

- **T1 — `fixtures/invariants/`, écrites à la main, versionnées.** ≈ 48 photos,
  36 textes, 6 albums, 2 tâches. Elles ne sont pas un échantillon : chaque ligne
  existe pour couvrir une branche.
  - une photo par valeur de `resolved_from` : `human`, `exif_arbitrated`,
    `logbook_bracket`, `album_month`, `album_year` ;
  - chacune croisée aux précisions applicables ;
  - une photo sans date résolue (le chemin `sans date` de §5.2) ;
  - **le cas `2000-12` de §7.3, verbatim** ;
  - **un `album_path` en NFD** — `1998-1999/1998-02-Maison rose Algès` ;
  - une photo dans 2 albums, une dans 4 (§B.5) ;
  - une photo dont la vignette manque sur disque → tuile grise nommant le
    fichier ;
  - une photo Q7 portant à la fois une date à la main et un EXIF qui la
    contredit ;
  - une proposition rang 3 **avec** fourchette et preuves, et une **sans**
    fourchette (`sans fourchette`, jamais un nombre non soutenu) ;
  - côté texte : un passage `confidence: uncertain`, un passage corrigé avec son
    original, un passage marqué « à revoir », un `spanSource: carried`, une page
    de journal couvrant plus de 30 jours, un passage web sans date.
  - **Origine** : rédigées à la main à partir des schémas mesurés de
    `docs/pipeline-inventory.md`. Un test vérifie que chacune valide le contrat.
- **T2 — volume synthétique, `fixtures/generateVolume.ts`, ignoré par git.**
  4 000 photos clonées des formes T1, avec l'histogramme de dates du tableau
  §2.1. **Pour la tenue de la grille et le défilement uniquement, jamais pour la
  correction.**
- **T3 — enregistré du réel, à SP2, ignoré par git.**
  `npm run fixtures:record` vide `GET /photos?limit=4000` et ses voisins dans
  `.fixtures-cache/`. Zéro règle dupliquée : la cascade reste au backend.
- **Vignettes.** 48 fichiers réels copiés une fois du volume vers
  `fixtures/thumbs/` (≈ 1,1 Mo, versionnés) pour que la CI n'ait jamais besoin
  du volume. Le miroir complet du périmètre (≈ 92 Mo) est produit par
  `fixtures/mirrorThumbs.ts` vers `public/thumbs/`, **en lecture seule sur la
  source**, ignoré par git.

```ts
export type ResolvedFrom =
  | 'human' | 'exif_arbitrated' | 'logbook_bracket' | 'album_month' | 'album_year';
export type DateKind = 'reading' | 'inference' | 'decision';
export type DatePrecision = 'day' | 'month' | 'year';

export interface Evidence { readonly id: string; readonly label: string; readonly href: string }

export interface ResolvedDate {
  readonly from: ResolvedFrom;
  readonly start: string;
  readonly end: string;
  readonly precision: DatePrecision;
  readonly arbitrationGapMonths: number | null;
  readonly bracketHours: number | null;
  readonly evidence: readonly Evidence[];
}

    case 'album_year': return 'inference';
    default: {

      throw new Error(`unmapped ResolvedFrom: ${String(unreachable)}`);
    }
  }
}
```

```ts
import { kindOf, type DateKind, type ResolvedDate } from './resolvedDate';

export interface FormattedDate {
  readonly kind: DateKind | 'absent';
  readonly glyph: '' | '≈' | '✓';
  readonly text: string;
  readonly detail: string | null;
  readonly label: string;
}

const MONTHS = [
  'janvier', 'février', 'mars', 'avril', 'mai', 'juin',
  'juillet', 'août', 'septembre', 'octobre', 'novembre', 'décembre',
] as const;

const GLYPH: Record<DateKind, FormattedDate['glyph']> = {
  reading: '', inference: '≈', decision: '✓',
};

const NATURE: Record<DateKind, string> = {
  reading: 'date lue', inference: 'date inférée', decision: 'date décidée à la main',
};

function renderText(date: ResolvedDate): string {
  const [year, month] = date.start.split('-');
  if (year === undefined || month === undefined) {
    throw new Error(`malformed resolved start: ${date.start}`);
  }
  switch (date.precision) {
    case 'day': return date.start;
    case 'month': {
      const name = MONTHS[Number(month) - 1];
      if (name === undefined) throw new Error(`malformed month: ${date.start}`);
      return `${name} ${year}`;
    }
    case 'year': return year;
  }
}

function renderDetail(date: ResolvedDate): string | null {
  if (date.from === 'logbook_bracket') {
    return date.bracketHours === null ? 'sans fourchette' : `± ${date.bracketHours} h`;
  }
  if (date.from === 'exif_arbitrated' && date.arbitrationGapMonths !== null) {
    return `EXIF, confirmé à ${date.arbitrationGapMonths} mois du mois d’album`;
  }
  return null;
}

export function formatResolvedDate(date: ResolvedDate | null): FormattedDate {
  if (date === null) {
    return { kind: 'absent', glyph: '', text: 'sans date', detail: null,
             label: 'sans date' };
  }
  const kind = kindOf(date.from);
  const text = renderText(date);
  return {
    kind, glyph: GLYPH[kind], text, detail: renderDetail(date),
    label: `${NATURE[kind]} : ${text}`,
  };
}
```

```ts
export interface DayInterval { readonly start: string; readonly end: string }

const MS_PER_DAY = 86_400_000;

/** Spec §4.1: two intervals overlap iff Pd ≤ Tf AND Td ≤ Pf. */
export function overlaps(a: DayInterval, b: DayInterval): boolean {
  return a.start <= b.end && b.start <= a.end;
}

/**
 * Present ONLY so the test suite can demonstrate that filtering does not use it.
 * Spec §7.3: a containment reading returns 0 photos where overlap returns 273.
 * Never call this from application code.
 */
export function contains(outer: DayInterval, inner: DayInterval): boolean {
  return outer.start <= inner.start && inner.end <= outer.end;
}

/** Inclusive width. A single day is 1, never 0. */
export function widthDays(i: DayInterval): number {
  const start = Date.parse(`${i.start}T00:00:00Z`);
  const end = Date.parse(`${i.end}T00:00:00Z`);
  if (Number.isNaN(start) || Number.isNaN(end)) {
    throw new Error(`malformed interval: ${i.start}..${i.end}`);
  }
  return Math.round((end - start) / MS_PER_DAY) + 1;
}
```

```ts
import { z } from 'zod';

export class ApiError extends Error {
  constructor(readonly status: number, readonly body: unknown, message: string) {
    super(message);
    this.name = 'ApiError';
  }
}

export class ContractError extends Error {
  constructor(readonly path: string, message: string) {
    super(message);
    this.name = 'ContractError';
  }
}

const base = (): string => import.meta.env['VITE_API_BASE_URL'] ?? '';

async function request<T>(
  path: string, schema: z.ZodType<T>, init?: RequestInit,
): Promise<T> {
  const response = await fetch(`${base()}${path}`, {
    ...init,
    headers: { 'content-type': 'application/json', ...init?.headers },
  });

  if (!response.ok) {
    const body: unknown = await response.json().catch(() => null);
    throw new ApiError(response.status, body,
      `${init?.method ?? 'GET'} ${path} failed with ${response.status}`);
  }

  const parsed = schema.safeParse(await response.json());
  if (!parsed.success) {
    const issue = parsed.error.issues[0];
    const dotted = issue?.path.join('.') ?? '';
    throw new ContractError(dotted,
      `${path} broke the contract at "${dotted}": ${issue?.message ?? 'unknown'}`);
  }
  return parsed.data;
}

export function apiGet<T>(path: string, schema: z.ZodType<T>, signal?: AbortSignal): Promise<T> {
  return request(path, schema, signal ? { signal } : {});
}

export function apiPost<T>(path: string, body: unknown, schema: z.ZodType<T>): Promise<T> {
  return request(path, schema, { method: 'POST', body: JSON.stringify(body) });
}
```

```ts
import { http, HttpResponse } from 'msw';
import { overlaps } from '../src/domain/interval';
import { store } from './store';

const KNOWN_PARAMS = new Set(['from', 'to', 'album', 'sort', 'limit', 'offset']);

export const handlers = [
  http.get('*/photos', ({ request }) => {
    const url = new URL(request.url);

    // Spec §9.6.1: an unknown query parameter is a 400, never ignored.
    for (const key of url.searchParams.keys()) {
      if (!KNOWN_PARAMS.has(key)) {
        return HttpResponse.json({ error: `unknown parameter: ${key}` }, { status: 400 });
      }
    }

    const from = url.searchParams.get('from');
    const to = url.searchParams.get('to');
    const album = url.searchParams.get('album');

    const kept = store.photos.filter((p) => {
      if (album !== null && p.albumPath.normalize('NFC') !== album.normalize('NFC')) return false;
      if (from === null || to === null) return true;
      if (p.resolved === null) return false;
      return overlaps(p.resolved, { start: from, end: to });
    });

    return HttpResponse.json({
      items: kept, total: kept.length, discarded: store.photos.length - kept.length,
    });
  }),
];
```

```tsx
import { formatResolvedDate } from '../../domain/formatResolvedDate';
import type { ResolvedDate } from '../../domain/resolvedDate';
import styles from './ResolvedDate.module.css';

interface Props {
  readonly date: ResolvedDate | null;
  readonly showDetail?: boolean;
}

/**
 * The ONLY component allowed to turn a date into text (spec §7.1).
 * The nature travels in three channels: the glyph, the accessible name,
 * and the colour — in that order of authority. Colour is never alone.
 */
export function ResolvedDateView({ date, showDetail = false }: Props): React.JSX.Element {
  const f = formatResolvedDate(date);
  return (
    <span className={styles.date} data-date-kind={f.kind} aria-label={f.label}>
      {f.glyph === '' ? null : <span aria-hidden="true">{f.glyph} </span>}
      {f.text}
      {showDetail && f.detail !== null
        ? <span className={styles.detail}> — {f.detail}</span>
        : null}
    </span>
  );
}
```
