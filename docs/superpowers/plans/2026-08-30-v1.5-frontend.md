# V1.5 — plan d'implémentation frontend

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Livrer les écrans de la 1.5 — la refonte de l'écran Textes, l'écran de datation du site, la sous-page Consigne, la Revue qui montre ce qu'elle exporte, et un panneau d'albums utilisable.

**Architecture:** Rien de nouveau dans la structure. L'URL reste la source de vérité des filtres, les schémas Zod valident toute réponse à l'entrée, les composants d'écran vivent dans `src/screens/` et les briques réutilisables dans `src/ui/<domaine>/`. Un seul composant reste autorisé à rendre une date.

**Tech Stack:** React 19, TypeScript strict, Vite, react-router 8, TanStack Query 5, Zod 4, Vitest + Testing Library + MSW.

**Spec:** `docs/spec-v1.5.md`

## Global Constraints

- **Le backend est en avance sur ce plan.** La tranche A du plan backend est livrée : quatre amendements commités (`d7442ad` note dérivée, `4f75a63` verrou de préfixe, `36f864e` répertoire de livraison, `d755cb1` borne unique du site), plus la cascade de date de page (`0d6b6fa`, `52a349d`). Les formes exactes sont dans `docs/api-contract.md`.
- **Tous les schémas du contrat client sont des `z.strictObject`.** Un champ ajouté par le serveur **fait échouer la validation**, il n'est pas ignoré. C'est pourquoi la tranche 1 est un correctif urgent et non une préparation.
- Une date ne se rend que par `ResolvedDateView` (`src/ui/date/ResolvedDate.tsx`). Le test `noBareDateRendering.test.ts` le vérifie ; ne pas le contourner.
- Les valeurs codées viennent de `src/shared/enums.ts`, jamais de littéraux en ligne.
- Pas de `any` hors donnée externe non typée. Types de retour explicites sur les composants exportés.
- Le mock MSW (`mocks/handlers.ts`) et le client changent **dans la même tâche**. La V1 a payé deux fois un mock d'accord avec un client faux.
- Commandes, depuis la racine : `npm test`, `npm run typecheck`, `npm run lint`.

## Ce que ce plan ne fait pas

À dire une fois, pour que personne ne l'invente :

- **Aucune virtualisation, aucune pagination, aucun `memo` spéculatif.** La liste de pages fait 155 lignes au maximum, la liste de documents web 60, celle des albums 82. La grille de photos tient déjà 3 930 tuiles sans rien de tout cela, mesuré. Si un écran rame, on le mesure d'abord.
- **Aucun découpage d'image.** La vignette d'une page est le scan entier réduit, servi par le serveur.
- **Aucun rendu des pages HTML du site.** Texte seul, et l'écran le dit.
- **Aucun geste de relecture des légendes de galerie.** Elles sont indicatives : affichées, jamais sélectionnables, jamais filtrées.
- **Aucun calcul de recouvrement côté client.** Les comptes viennent du serveur ; les dupliquer en TypeScript produirait un chiffre qui finirait par contredire le reste de l'application.

export function sortAlbumsByPath(albums: readonly Album[]): Album[] {
  // `caseFirst: 'upper'` plutôt que le défaut : sans lui, deux albums du même
  // mois s'inversent selon leur majuscule, ce qui se lit comme un tri cassé.

  return [...albums].sort((a, b) => collator.compare(a.path, b.path));
}

## Plan de tests

| Niveau | Ce qu'il prouve | Où |
|:--|:--|:--|
| **Domaine** (`src/domain/*.test.ts`) | Le tri des albums, l'état des filtres et son aller-retour par l'URL, le titre d'attribution. Aucun rendu, aucun réseau. | `domain/` |
| **Contrat** (`src/api/contract/*.test.ts`) | Qu'un schéma accepte ce que le serveur envoie et refuse ce qu'il n'enverrait pas. | `api/contract/` |
| **Composant** (`*.test.tsx`) | Le comportement vu par l'utilisateur, à travers les rôles et les libellés, contre MSW. | `ui/`, `screens/` |
| **Formes réelles** (`liveShapes.itest.ts`) | Que le client et le serveur sont d'accord — la seule question que les trois niveaux au-dessus ne posent pas. | projet `live` |

Trois règles pour ces tests, tirées de ce que la V1 a coûté :

**Faire passer l'état par le même aller-retour que l'écran.** Le harnais de `FilterPanel.test.tsx` stockait un `FilterState` brut au lieu de le faire transiter par `toSearchParams`/`fromSearchParams`, et le défaut « impossible de saisir une date » a survécu à 588 tests verts. Tout test de filtre passe par l'URL.

**Inspecter le corps réellement envoyé, pas seulement la réponse du mock.** Le défaut « impossible d'ajouter une image » venait d'un mock qui acceptait la même forme fausse que le client envoyait. Les tests de mutation lisent la requête interceptée.

**Démonter et remonter pour prouver qu'un enregistrement a atteint le serveur.** Un test qui vérifie la frappe locale passe sur un bouton câblé à rien — c'est exactement ce qu'a fait le test « the brief is editable ».
